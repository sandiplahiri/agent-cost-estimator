# Create a cost model for an agent suite

This guide explains how to build, review, save, and export a monthly cost model in Agent Ledger. It works for one agent or a suite of hundreds. The result is an estimate based on explicit workload and execution assumptions, with separate model-token, tool, runtime, and additional costs.

The app does not execute your agents or measure their usage. Starter profiles and Low/High scenarios are illustrative planning inputs, not benchmarks or statistical confidence intervals. Replace them with your architecture assumptions and, when available, observed usage.

## 1. Prepare your inputs

Before entering values, list the agents and the business outcome that one invocation of each agent completes. An invocation is one execution of an agent's use case; it may contain several steps and several model calls.

For each agent, gather:

| Input | What to record |
| --- | --- |
| Identity | A unique agent name and a short business use case name and description. |
| Direct workload | Users per agent per day and average invocations per user per agent per day. For a called agent, identify the steps that invoke it instead. |
| Ordered steps | What happens in one invocation, whether each step invokes a model or another suite agent, and how often the step runs. |
| Model choices | Exact provider/model identity for each model step, including alternatives and their selection probabilities. |
| Execution assumptions | Normal model calls, average input/output tokens per call, additional retry attempts, and cache fractions. |
| Pricing | Input/output and applicable cache rates, currency, channel, region, contract or service tier, source, and retrieval date. |
| Other spending | Tool charges, shared runtime charges, recurring costs, and one-time costs. |
| Uncertainty | Which inputs are estimated, their evidence, and plausible Low/Expected/High alternatives. |

Separate agent identity, step complexity, model choice, and workload. For example, a support agent can classify a request with a simple step and draft an answer with a high-complexity step. It remains one agent with one invocation volume.

Record assumptions in **Customer assumptions & notes**, including the planning period, data sources, exclusions, and why uncertain values were chosen. Do not put credentials or sensitive customer prompts into notes or exports.

## 2. Start the app and name the estimate

Follow [Run locally in the README](../README.md#run-locally), then open **http://127.0.0.1:8000**. Routine estimates require no provider API keys and make no paid model calls.

Choose **New estimate** when starting a separate budget and enter an **Estimate name**, such as `Customer support suite — initial plan`. Use **Save estimate** after meaningful changes. Switching between the navigation views keeps the same estimate draft.

## 3. Define the agents

Open **Agent inventory**. Choose the entry method that matches your starting material:

- **Add agent**: Create an individual agent, enter its name, business use case name and description, and daily workload, then define its steps. Use this for a small suite or agents with different workflows.
- **+ Bulk add**: Create many agents with starter simple, medium, or high assumptions. The category counts must add to the total, and each populated category needs both daily workload inputs. Every agent gets a distinct identity. Replace generated names and pending use case descriptions with meaningful values and customize steps afterward.
- **Template** and **Import**: Populate an agent spreadsheet and review it before applying. See [the spreadsheet workflow](#12-build-or-update-a-suite-from-a-spreadsheet).

**Bulk add replaces the current inventory and its invocation links.** Save or export JSON first if you need to keep an existing suite.

Use **Edit** on an inventory row to change one agent. Editing an agent that shares execution settings with others affects that individual only when you apply changes. Closing the editor without applying leaves the existing estimate unchanged. The individual editor keeps the agent ID fixed.

The inventory shows distinct callers and callees derived from invocation links. These counts are not model calls or monthly workload and cannot be edited directly.

## 4. Set workload with explicit units

For a directly invoked agent, enter:

- **Users per agent per day**: The average number of users generating work for that agent each planning day.
- **Invocations per user per agent per day**: The average executions of that agent's use case generated by each user each planning day.

The app uses a **30-day planning month**:

```text
monthly invocations per agent
  = users per agent per day
  × invocations per user per agent per day
  × 30
```

For example, 100 users/day × 2 invocations/user/day × 30 days gives **6,000 invocations per agent per month**. Ten separate agents with that same workload contribute 60,000 invocations, before any delegated work.

Use averages across the planning month. If usage occurs on 22 days, either convert it to a 30-day daily average or use an explicit manual monthly source through spreadsheet/JSON import. For example, 100 users × 2 invocations × 22 days is 4,400 monthly invocations; entering 100 and 2 directly would produce 6,000.

Both daily fields are required for new direct-volume entries. Zero is a valid known value; a blank is missing. Expected workload and model-call averages may be fractional, while agent counts are integers.

Incoming agent links replace a child's direct workload with derived workload. Its daily inputs remain stored for recovery, but they do not add to the derived volume. The current model cannot combine independent direct traffic and incoming delegated traffic for the same agent. If both are needed, model separate agent definitions with clearly separated workloads and document the assumption.

## 5. Define each agent's steps

In **Edit agent**, use the ordered **Steps** list. Where offered, **Use detailed workflow** turns an aggregate definition into explicit steps. A detailed workflow replaces that agent's aggregate execution contribution.

Each step chooses one action:

| Action | Meaning |
| --- | --- |
| **Invoke model** | Select exactly one model option when the step runs. That option has its own model-call and token assumptions. |
| **Invoke agent** | Select exactly one named individual suite agent and invoke it once when the step runs. The child uses its own workflow and model assumptions. |

Give each step a descriptive name. A model step also chooses a **complexity profile**: simple, medium, high, or a custom profile. Profiles supply starter execution assumptions; they do not choose a provider or determine the agent's use case.

Expand **Step execution details** to adjust execution probability and model assumptions. The two probabilities mean different things:

- **Execution probability** is the chance that this step runs during one agent invocation. `1` means always, `0.2` means an expected 20% of invocations, and `0` means no execution.
- **Option probability** is the chance of selecting a target, conditional on the step running. The nonempty option list must total **exactly 1.0**, even for an optional step.

For example, a review step that runs 20% of the time and selects model A with probability 0.75 or model B with probability 0.25 contributes 0.15 expected A selections and 0.05 expected B selections per agent invocation.

One step cannot invoke a model and an agent together. If two targets must both run, create two steps. To invoke the same child twice, use two agent steps; an agent option has no repetition count. Each individual child can appear only once within a step's option list.

New options begin at probability zero. Choose their targets and rebalance the distribution before applying. Changing a step's action clears the previous target list; **Undo action change** is available within the editor.

### Choose execution assumptions for model options

| Field | Unit and interpretation |
| --- | --- |
| Model calls | Normal calls when this model option is selected; includes ordinary tool/revision cycles, excludes additional retry attempts. |
| Input tokens | Average tokens per model call, including instructions, history, retrieval, tool definitions, and tool results actually sent. |
| Output tokens | Average billable output tokens per model call, including billable reasoning already counted as output. |
| Additional attempt rate | Extra attempts divided by normal calls. `0.05` means 5 additional attempts per 100 normal calls. |
| Cached-read fraction | Fraction of total input tokens billed at the cached-read rate. |
| Cache-write fraction | Fraction of total input tokens billed at the supplied base/short-duration cache-write rate. |

Retries are not the same as failure probability or a retry limit. The current average-based calculation assumes retry attempts use the same average input/output sizes as normal calls. Do not add billable reasoning again if it is already included in output.

Cached reads and writes partition input: their fractions must be nonnegative and sum to at most 1. The remaining fraction is uncached input. For example, 2,000 input tokens with a cached-read fraction of 0.5 contain 1,000 cached-read and 1,000 uncached tokens, not 3,000 total input tokens.

### Use profiles without losing explicit assumptions

The bundled profiles start with:

| Profile | Normal calls/invocation | Input tokens/call | Output tokens/call | Additional attempt rate |
| --- | ---: | ---: | ---: | ---: |
| Simple | 1 | 2,000 | 500 | 0.02 |
| Medium | 4 | 6,000 | 1,000 | 0.05 |
| High | 10 | 15,000 | 2,000 | 0.10 |

These values are editable planning assumptions. If an agent has several explicit steps, set each step's calls to the work that step actually performs; do not copy a whole-agent call budget onto every step.

Open **Complexity profiles** to edit defaults or choose **Add custom category**. Custom names must be unique. A global custom category becomes available to new estimates; an older estimate can attach it using **Use [category]**. Referenced custom categories cannot be deleted until their agent defaults and steps, including references in saved estimates, have been reassigned.

For aggregate definitions, effective assumptions follow profile defaults → edited profile → agent overrides → scenario multipliers/model override. Explicit zeros remain overrides. Detailed model options have explicit execution values and receive scenario multipliers. Changing an existing step's profile preserves its entered models and execution numbers; inspect and edit those numbers if you intend different behavior. Changing a model also preserves execution assumptions.

## 6. Select models and check prices

Choose a specific model for every model option. Model selections start empty, so a newly created agent may show incomplete pricing until you select one.

Open **Model pricing** to review the selected rates and their provenance. The installed LiteLLM catalog is available locally. A catalog entry does not guarantee that the model is available in your deployment or that every applicable billing category has a price.

Check the provider, model, price-relevant channel/region/service tier, currency, rates per million tokens, source, and retrieval date. A retrieval date is not necessarily the provider's price effective date.

For missing or negotiated prices:

1. Choose **Add custom rates**.
2. Enter a unique model ID, such as `customer/support-model-contract-a`, and the provider, source type, channel, and region.
3. Enter input/output and applicable cache rates **per 1,000,000 tokens** in the selected currency. Convert a per-1,000-token quote by multiplying its rate by 1,000.
4. For non-USD prices, enter **USD per 1 currency unit** and an **FX rate source**. The app calculates in USD and saves the original rates and conversion snapshot.
5. Select the custom model ID on the applicable steps and record the contract/source details in your notes.

Use separate IDs for distinct contracts, regions, or service tiers. A custom per-token rate labeled self-hosted does not calculate GPU capacity or utilization costs.

Missing pricing means **Incomplete** or a partial known subtotal, never a complete zero bill. If a workload includes cache writes and the model lacks a write rate, supply an applicable rate. Set the fraction to zero only when there are genuinely no cache writes.

Supported pricing includes text input/output, cached reads, base-duration cache writes, and catalog context/batch rates where available and supported. Request-level tiers are applied before monthly scaling. If requests straddle a context threshold, split them into representative model options or steps with distinct per-call sizes rather than relying on an average that hides the higher tier.

For reproducibility, saved estimates keep their prices. **Refresh catalog** explicitly fetches the published catalog and previews the change before you apply updated prices to the draft. It requires network access and sends no customer inputs. Save after applying a refresh; export the previous estimate first if you need both versions. A failed refresh retains usable saved prices.

## 7. Link agents and derive child workload

Create the agents first, then configure the caller's **Invoke agent** steps. Open **Agent suite graph** to inspect the resulting relationships. Links come from step options; the graph is not a separate workload model.

For each agent option:

```text
child monthly invocations from this option
  = caller monthly invocations
  × step execution probability
  × child selection probability
```

A caller with 3,000 monthly invocations and an always-executed routing step selecting Writer at 0.8 and Escalation at 0.2 produces 2,400 Writer and 600 Escalation invocations. Contributions from several callers or several steps add.

The child receives all work assigned to its individual identity. Other agents that previously shared its settings retain their own direct workload. Removing the final option calling a child restores its retained direct volume, so check that recovery volume before removing links.

The suite total counts each agent's own model/tool execution once at its direct or derived volume. The caller's agent-step **Expected action cost** explains the selected child's loaded cost, including downstream work. Do not add that explanation to the child's own cost again.

Self-calls, dependency cycles, missing targets, and invalid probability distributions are rejected. Model retry rates and scenario call multipliers do not repeat child-agent invocations. The scenario volume multiplier scales direct roots and propagates through descendants once.

**Copy** creates an independent agent with copied steps, tools, and outgoing choices, no incoming links, and zero direct workload. Give the copy direct volume or connect it before expecting monthly spending from it.

## 8. Add tool, harness, and additional costs

Add tool charges in the agent editor when they depend on agent execution. Enter the USD unit cost, expected units per invocation, and tool probability. Optionally attach a charge to a step so its execution probability also applies. These charges are separate from model tokens.

Open **Agent harness** for one shared runtime entry. Select a type, or **None (explicitly no cost)** if your budget excludes runtime charges. The implemented formula is:

```text
monthly harness cost
  = fixed monthly fee
  + USD per agent invocation × all monthly agent invocations
  + USD per step execution × all monthly step executions
```

The invocation driver includes both roots and derived children. A model step's multiple model calls or retries do not turn it into multiple step executions. Fixed fees remain at zero workload. Allocation by invocations affects per-agent and use-case reporting without changing the suite total.

Open **Additional costs** for named items with a USD unit cost, quantity, and monthly or one-time frequency. For example, enter recurring storage here if it is not already covered by the harness. Avoid charging the same hosting, tool, or cache-storage expense twice.

Monthly additional items remain fixed across scenarios. One-time items are excluded from the monthly total. First-year cost assumes 12 unchanged recurring months plus one-time items.

## 9. Define Low, Expected, and High scenarios

Open **Scenarios** and set explicit multipliers:

| Control | Effect |
| --- | --- |
| Invocation volume × | Scales direct workload and its derived descendants. |
| Calls per invocation × | Scales normal model calls. |
| Input tokens per call × | Scales each model call's input size; may change its pricing tier. |
| Output tokens per call × | Scales billable output size. |
| Additional attempts × | Scales the additional attempt rate, not the whole bill. |
| Model override | Optionally replaces model choices in that scenario. |

`1` means unchanged. For example, a baseline additional attempt rate of 0.05 with a retry multiplier of 2 becomes 0.10, giving an attempt multiplier of 1.10.

The starter Low scenario uses 0.75× input/output token sizes; High uses 1.5×. Other starter multipliers remain 1. Replace these with defensible alternatives. Keep Expected multipliers at 1 when your baseline inputs already describe the expected workload, or document why they differ.

**Step execution details** also accepts optional Low/High step execution probabilities. Agent-option Low/High selection probabilities can be supplied through JSON or the **Step options** spreadsheet; each scenario distribution must still total 1.0. Blank scenario probabilities inherit the baseline, while explicit zero remains zero.

These are parameter changes, not a hidden percentage adjustment to the final bill. Additional fixed costs do not scale with token sizes. Low/High are planning cases; changing models or crossing a tier can affect cost ordering, so review the actual results.

## 10. Work through a complete example

This synthetic example uses invented custom USD rates for arithmetic clarity. It makes no claim about any provider's current prices or typical usage.

Create two custom model IDs in **Model pricing**:

| Custom model ID | Input USD/1M tokens | Output USD/1M tokens |
| --- | ---: | ---: |
| `example/small` | 1.00 | 4.00 |
| `example/large` | 3.00 | 12.00 |

Create three agents, each with a business use case:

| Agent | Business use case | Baseline monthly workload |
| --- | --- | ---: |
| Router | Classify and route a support request | 100 users/day × 1 invocation/user/day × 30 = 3,000 |
| Writer | Draft a routine support response | Derived from Router: 2,400 |
| Escalation | Resolve a complex support request | Derived from Router: 600 |

Initially enter zero for both daily inputs on Writer and Escalation, then link them from Router. Their retained zero inputs keep them inactive if the links are later removed.

Configure the steps below. Every step executes with probability 1. Every model option has probability 1. Set both cache fractions to zero. Choose any appropriate profile labels, but explicitly enter all the numeric values in this table instead of retaining starter values.

| Agent and step | Action/target | Normal calls when selected | Input tokens/call | Output tokens/call | Additional attempt rate |
| --- | --- | ---: | ---: | ---: | ---: |
| Router: Classify | Model: `example/small` | 1 | 1,000 | 100 | 0 |
| Router: Route | Agent: Writer probability 0.8; Escalation probability 0.2 | One selected child invocation | — | — | — |
| Writer: Draft | Model: `example/large` | 2 | 2,000 | 500 | 0.05 |
| Escalation: Resolve | Model: `example/large` | 1 | 4,000 | 1,000 | 0.10 |

With uniform prices, no caching, and Expected scenario multipliers of 1:

```text
monthly model calls including extra attempts
  = agent monthly invocations × step probability × model option probability
  × normal calls × (1 + additional attempt rate)

monthly token cost
  = monthly calls × (input tokens/call × input USD/1M
                  + output tokens/call × output USD/1M) / 1,000,000
```

Independent calculations give:

| Agent | Monthly model calls, including retries | Monthly input tokens | Monthly output tokens | Monthly token cost, USD |
| --- | ---: | ---: | ---: | ---: |
| Router | 3,000 | 3,000,000 | 300,000 | 4.20 |
| Writer | 2,400 × 2 × 1.05 = 5,040 | 10,080,000 | 2,520,000 | 60.48 |
| Escalation | 600 × 1 × 1.10 = 660 | 2,640,000 | 660,000 | 15.84 |
| **Suite** | **8,700** | **15,720,000** | **3,480,000** | **80.52** |

The suite has **19,200,000 total tokens**, **6,000 agent invocations**, and **9,000 step executions** per month. Router contributes two executed steps for each of its 3,000 invocations; each child contributes one step per invocation. Input cost is USD 41.16 and output cost is USD 39.36.

Set the harness to a non-None type with a USD 50 monthly fixed fee, USD 0.001 per agent invocation, and USD 0.002 per step execution:

```text
harness = 50 + (6,000 × 0.001) + (9,000 × 0.002) = USD 74.00/month
```

Add one monthly cost with unit cost USD 20 and quantity 1, plus one one-time cost of USD 100 with quantity 1. Add no tool charges. With the starter token-size scenarios and all other factors unchanged, expect:

| Scenario | Token cost, USD/month | Harness, USD/month | Other costs, USD/month | Total cost, USD/month |
| --- | ---: | ---: | ---: | ---: |
| Low: 0.75× input/output | 60.39 | 74.00 | 20.00 | 154.39 |
| Expected: 1× input/output | 80.52 | 74.00 | 20.00 | 174.52 |
| High: 1.5× input/output | 120.78 | 74.00 | 20.00 | 214.78 |

The Expected first-year amount is `174.52 × 12 + 100 = USD 2,194.24`. This assumes unchanged monthly usage. The USD 100 one-time item does not appear in monthly Other costs.

## 11. Review and reconcile the budget

Open **Dashboard** and inspect **Monthly token and cost summary**. Each Low/Expected/High row consolidates the entire suite:

- **Input/output tokens and costs** show that scenario's actual modeled usage. Input cost includes uncached input, cached reads, and cache writes; output includes configured billable output.
- **Total token cost** is model-token spending only.
- **Harness cost** is the shared runtime charge.
- **Other costs** combines tools and recurring additional items, excluding one-time costs.
- **Total cost** is token cost + harness cost + Other costs.

Check completeness on each component. Known fixed harness or additional costs can remain complete while model pricing is incomplete. A partial amount is a known subtotal, not a final budget.

Use **Top agents by cost** to review the five individual agents with the highest Expected monthly token cost. It excludes tool, harness, and additional charges. Missing prices or workload can make the ranking incomplete.

In **Agent inventory**, **Total Cost** includes the agent's own Expected model/tool spending plus allocated harness. Child costs stay on child rows. Inventory amounts need not sum to the full suite amount when there are suite-level additional costs or unallocated fixed harness at zero volume.

The agent and model-step **Cost** sections show Expected token counts and costs from draft edits. Model-step token costs reconcile to the agent's token cost. Agent-step loaded action costs are attribution explanations, not additional token charges.

Before accepting the estimate, check that every named agent is counted once, every direct workload has a source, derived volumes match caller probabilities, every model option has applicable prices, and profile/call/token/retry values describe the actual step. For a large suite, inspect the highest-cost agents first, then review missing or uncertain inputs.

## 12. Build or update a suite from a spreadsheet

In **Agent inventory**, download **Template** and read its **Instructions** sheet. Use a values-only `.xlsx` file and keep the supplied column names.

For ordinary direct-volume rows in **Agents**, fill in:

| Column | Accepted value/unit |
| --- | --- |
| `name` | Agent name. |
| `complexity` | `simple`, `medium`, `high`, or a custom profile already attached to the estimate; a starting default for execution. |
| `count` | Nonnegative integer number of agents sharing this definition. Use 1 for individually identified agents. |
| `volume_source` | `daily_users`, or `manual` for an explicit monthly-volume row. |
| `users_per_day` | Required average users per agent per day for daily rows. |
| `invocations_per_user_per_agent_per_day` | Required average invocations per user per agent per day for daily rows. |
| `invocations` | Monthly invocations **per agent** for manual rows; ignored for daily rows. |
| `model_id` | Exact catalog/custom ID for aggregate execution; omit only if intentionally incomplete or supplying detailed model steps. |
| `calls`, `input_tokens`, `output_tokens` | Optional aggregate normal calls/invocation and input/output tokens/call. |
| `retry_rate`, `cache_fraction`, `cache_write_fraction` | Optional fractions with the meanings described above. Blank inherits; zero is explicit. |
| `agent_id` | Optional stable individual ID for a count-one row. Use explicit IDs when steps target these agents. |
| `business_use_case_description` | Short description; missing descriptions are marked pending. Edit the use case name in the app afterward. |
| `row_id` | Definition ID used to associate rows with the optional **Step options** sheet. |

Each counted definition creates distinct identities. Do not list the same agents again as extra rows to represent overrides; customize the individual afterward. Profiles identify execution assumptions, not separate business agents.

To import detailed workflows, add one **Step options** row per target option:

1. Reference the owner's `Agents.row_id`; supply `step_id`, `step_name`, a positive unique step `order`, and `action_type` (`model` or `agent`).
2. Supply an explicit option `probability`; all options for a step must total 1.0.
3. For model options, supply `model_id`, the step's `complexity`, and execution assumptions. For agent options, supply `child_agent_id` referencing an individual `Agents.agent_id` in the same import, with count 1.
4. Keep shared step fields consistent across its option rows. Optionally supply `execution_probability`, Low/High execution probabilities, and Low/High agent-option probabilities. Additional child invocations require additional steps.

Choose **Import**, select the file, read the validation errors or replacement preview, and apply only when correct. Imports replace the full inventory and its links after validation; they do not merge additional agents into the existing inventory. The current estimate's pricing, profiles, and global scenarios remain in place. Without **Step options**, rebuild invocation relationships in the app.

Files are limited to 5 MB, 30 MB expanded, 1,000 agent rows, and 5,000 step-option rows. Formula cells, macros, and external workbook links are rejected. If validation fails, fix the indicated rows/columns and retry; the current draft is not partially replaced.

Spreadsheet import is an inventory/workflow tool. Use JSON for a complete backup of identities, tools, pricing, profiles, scenarios, and all estimate settings.

## 13. Save, reopen, and export a reviewable model

Choose **Save estimate**, then **Export JSON** in Agent inventory for a portable, complete backup. **Open estimate** reloads a saved estimate with its original pricing snapshot. JSON import accepts the current versioned estimate schema; older unsupported schemas are rejected without a conversion workflow.

Browser drafts aid recovery, but use an explicit save and JSON backup for handoff. Local saved data is stored in `data/estimates.sqlite3` unless `ESTIMATOR_DB` overrides it. To back up the database file, stop the server first.

Choose **Export Excel** to deliver the current calculated assumptions and frozen prices. Review these sheets:

| Sheets | Purpose |
| --- | --- |
| **Summary**, **Monthly scenario summary** | Monthly scenario totals, components, annualized amounts, and completeness. |
| **Agents**, **Agent identities**, **Volume** | Definitions, individual identities, workload sources, and volumes. |
| **Calculations**, **Category usage**, **Category costs**, **Monthly category summary** | Model usage, selected effective rates, token-type costs, profile summaries, and daily averages. |
| **Step options**, **Step actions**, **Agent links**, **Use cases** | Workflow definitions, distributions, derived workload, and explanatory loaded use-case costs. |
| **Tool costs**, **Harness**, **Additional costs** | Non-token spending and its assumptions. |
| **Profiles**, **Scenarios**, **Pricing**, **Read me** | Effective configuration, price provenance, and recalculation limits. |

Open the workbook in Excel or compatible calculation software and let formulas recalculate. Compare the scenario amounts with Dashboard, including partial/incomplete labels. For the worked example, compare against the independent numbers in this guide.

The workbook includes formulas for supported model/tool/harness calculations, but is not a complete graph editor. Derived graph volumes and loaded use-case/step-action explanations are precomputed. Editing graph links or upstream volumes requires changing the app model and re-exporting. Editing profile/scenario/pricing snapshot sheets does not automatically update effective inputs in **Calculations**. Crossing a context tier or changing FX requires updating effective rates or re-exporting.

Profile summaries allocate model steps by their effective profile. An agent with several profiles remains one agent; overlapping profile invocation counts are not a disjoint suite workload and must not be added as such.

Keep the exported workbook, JSON snapshot, planning notes, and any source spreadsheet together so another reviewer can reproduce the budget.

## 14. Refine the model safely

As architecture details become clearer, replace starter assumptions with representative calls and measured averages. Track which inputs changed and compare resulting scenarios before updating the customer budget.

Use **Reset parameters** in Complexity profiles only after reviewing its scope. It restores starter execution assumptions and can also clear individual/scenario execution overrides. Agent identities, counts, workload, model choices, exclusive step actions/targets, custom prices, and additional costs are preserved. **Undo** restores the previous applied state; save a snapshot before a large revision because Undo is not a full history.

To delete an agent, use **Delete** in inventory or **Delete agent** in its editor. Review the named confirmation. An agent referenced by another step, even at probability zero, cannot be deleted until those options are removed or retargeted with valid distributions. Deleting a caller recalculates child workload and may restore a child's retained direct inputs. Save to persist the deletion.

The implemented model uses averages and expected probabilities. It does not provide live execution measurement, business-event mapping, context carryover, Monte Carlo confidence intervals, GPU capacity planning, monthly volume-tier billing, or a full provider billing simulator. Multimodal charges, separate reasoning rates, hosted tools, long-duration cache writes, and advanced platform contracts may require an explicitly documented approximation or separate additional cost. See [implementation status](AGENTIC_IMPLEMENTATION.md) for the supported scope.

Before handing over the model, resolve missing prices/workload or label the budget partial, document approximations and exclusions, verify that monthly components reconcile, save the estimate, and retain both Excel and JSON deliverables.
